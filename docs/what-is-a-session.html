What is a session

Jarvis creates GPT Live-1 sessions through its Bun server. WebRTC carries the running conversation, while the browser tracks captions, playback, backend actions, and final usage.

GPT Live-1

Creation, conversation, and display state

The browser captures a microphone track, creates the oai-events data channel, and gathers an SDP offer. POST /session sends that offer and pacing preferences to the Bun BFF. The BFF uses its server-only OPENAI_API_KEY to create the GPT-Live session.

The HTTP response is the session ID and SDP answer. The browser applies the answer and waits for session.started. The running conversation carries microphone audio, assistant audio, captions, and delegated backend events over WebRTC. Display state can change many times within one session.

Connection sequence

SDP goes through the BFF; media goes directly to OpenAI.

  1. Open GET /session as a lifetime stream and wait for its first frame.
  2. Capture the microphone and create the data channel.
  3. Set the local SDP and wait for ICE gathering, up to 10 seconds.
  4. POST JSON containing sdp and preferences to /session.
  5. The BFF posts JSON containing session configuration and transport: { type: "webrtc", sdp } to /v1/live/sessions.
  6. Read session.id and transport.sdp from the answer. Wait up to 20 seconds for session.started after setting the remote description.
  7. Exchange audio on media tracks and JSON events on the data channel.

The BFF has no role in microphone streaming or tool execution after session creation. It keeps the API key, model selection, backend tool schema, and backend output-token limit on the server.

Credentials

The API key stays on the server.

GPT-Live does not use the old Realtime client-secret flow. The browser receives an opaque session ID and an SDP answer. It does not send a bearer token to OpenAI or call realtime/calls.

Existing tokenEndpoint and token-endpoint host options retain their names for compatibility. Their value is now the URL of the Live SDP broker.

Lifetime

Close the session before releasing its media.

await viz.disconnect() stops the microphone tracks, sends session.close, and waits for session.closed. That final event supplies cumulative voice usage in seconds. Only then does the transport close the data channel and peer connection. A 15 second timeout releases those resources and reports unconfirmed final usage. A provider error or a failed backend response does not end the session; the transport reports it and keeps the call open.

The browser holds a lifetime stream to the Bun server. Server shutdown ends the stream and immediately closes browser media and WebRTC after attempting session.close. A stalled stream times out after 15 seconds without a heartbeat. This forced shutdown reports unconfirmed final usage and never reconnects automatically.

unmount() starts that cleanup without waiting. Disconnect first if the host needs the final usage event. A backend response completing or a caption arriving does not end the voice session.

Limits and delegation

The session budget limits creation requests.

The BFF applies per-origin rate and session budgets, and it caps concurrent lifetime streams per origin. Those counters do not limit conversation duration. MAX_OUTPUT_TOKENS limits delegated Responses output, not spoken audio. Voice usage is cumulative; do not sum usage snapshots.

GPT Live-1 handles speech. A separately configured Responses model reasons and chooses the bounded perform_ui_actions tool. The browser validates and executes those actions. Speech can overlap backend work and does not cancel it. Captions retain independent user and assistant fragments and timestamps.
